۱. معرفی و دامنه پروژه

PyLex Studio یک برنامه دسکتاپ برای نوشتن، بررسی، اجرا و مدیریت پروژه‌های Python است. رابط گرافیکی با Tkinter و ttk ساخته شده و منطق برنامه در ماژول‌های جداگانه نگهداری می‌شود تا اجزای رابط کاربری، تحلیل کد و سرویس‌های پردازه‌ای تا حد ممکن از یکدیگر مستقل باشند.

این پروژه در ابتدا بر ویرایش کد و تحلیل مقدماتی لغوی و نحوی تمرکز داشت و در نسخه‌های بعدی به محیط کاری یکپارچه‌تری گسترش یافت: مدیریت فایل و Workspace، مفسر و محیط مجازی، اجرای غیرهم‌زمان، دیباگر، ترمینال، ابزارهای کیفیت کد و پنل Git.

مرز مهم محصول: PyLex Studio یک محیط توسعه دسکتاپ سبک است؛ در نسخه 2.0.2 ادعای برابری با IDEهای بزرگ، پشتیبانی کامل از Language Server Protocol یا اجرای امن در Sandbox مطرح نمی‌کند.

اهداف اصلی

  • فراهم‌کردن گردش کار ساده برای ویرایش و اجرای کد Python.
  • تفکیک رنگ‌بندی ویرایشگر از تحلیل لغوی و اعتبارسنجی نحوی.
  • استفاده از مفسر انتخاب‌شده پروژه در اجرا، دیباگ و ابزارهای کیفیت.
  • نمایش خروجی، خطاها و تشخیص‌های قابل کلیک با محل دقیق در فایل.
  • اجرای کارهای زمان‌بر خارج از حلقه اصلی رابط Tkinter.
  • نگهداری کد ماژولار و پوشش رفتارهای مهم با آزمون خودکار.

۳. نیازمندی‌ها و نصب

پیش‌نیازها

  • Python نسخه 3.10 یا جدیدتر.
  • Tkinter/ttk؛ در بیشتر نصب‌های رسمی Python روی Windows موجود است. در توزیع‌های Linux ممکن است بسته جداگانه‌ای مانند python3-tk لازم باشد.
  • Git برای پنل کنترل نسخه و عملیات مخزن.
  • Pygments برای رنگ‌بندی نحوی.
  • Black، Ruff و pytest برای امکانات قالب‌بندی، lint و Test Explorer؛ این ابزارها در فایل نیازمندی پروژه تعریف شده‌اند.

دریافت سورس

git clone https://github.com/Amirh-Darvishi/pylex-studio.git
cd pylex-studio

ساخت محیط مجازی

# Windows PowerShell
python -m venv .venv
.venv\Scripts\Activate.ps1

# Linux / macOS
python3 -m venv .venv
source .venv/bin/activate

اگر PowerShell اجرای اسکریپت فعال‌سازی را مسدود کرد، می‌توانید به‌جای تغییر سیاست سیستم، مستقیماً از مفسر محیط مجازی استفاده کنید: ..venv\Scripts\python.exe -m pip ... و ..venv\Scripts\python.exe main.py.

نصب وابستگی‌ها و اجرا

python -m pip install --upgrade pip
python -m pip install -r requirements.txt
python main.py

فایل requirements.txt فقط وابستگی‌های زمان اجرای برنامه مانند Pygments و ttkbootstrap را فهرست می‌کند. برای مشارکت در توسعه، اجرای آزمون‌ها و کنترل کیفیت، ابتدا python -m pip install -r requirements-dev.txt را اجرا کنید؛ این فایل علاوه بر وابستگی‌های اصلی، pytest، Black و Ruff را نصب می‌کند.

چرا venv و نه Docker؟

PyLex Studio برنامه دسکتاپ Tkinter است و باید به پنجره‌های سیستم‌عامل دسترسی داشته باشد. اجرای GUI داخل Docker معمولاً به پیکربندی اضافی X11/Wayland یا راهکارهای نمایشگر نیاز دارد. محیط مجازی Python نصب ساده‌تر، تفکیک وابستگی‌ها و تجربه مناسب‌تری برای توسعه دسکتاپ فراهم می‌کند. Docker می‌تواند برای سناریوهای CI یا محیط‌های کنترل‌شده جداگانه مفید باشد، اما روش پیش‌فرض اجرای برنامه نیست.

۴. شروع سریع

  1. برنامه را با python main.py اجرا کنید.
  2. از منوی File یک فایل Python باز کنید یا سند جدید بسازید.
  3. برای پروژه چندفایلی، پوشه ریشه پروژه را به‌عنوان Workspace باز کنید.
  4. کد را بنویسید و با Ctrl+S ذخیره کنید.
  5. برای اجرای کد از Run یا F5 استفاده کنید؛ خروجی را در پنل Output ببینید.
  6. برای بررسی ساختار کد از Analyze All یا F6 استفاده کنید.
  7. در صورت نیاز مفسر پروژه را از Tools → Python Interpreter انتخاب کنید.
  8. برای دیباگ، ترمینال، کیفیت کد و Git از منوی Tools یا پنل مربوطه استفاده کنید.
برای اجرای یک فایل که به ماژول‌های هم‌سطح یا پوشه‌های پروژه وابسته است، ابتدا Workspace را روی ریشه پروژه تنظیم کنید. این کار مسیر کاری و مسیر جست‌وجوی import را درست‌تر می‌کند.

۵. محیط برنامه و گردش کار

پنجره اصلی اجزای ویرایش، پنل پروژه و پنل‌های نتیجه را کنار هم قرار می‌دهد. بسته به فضای موجود، می‌توان پنل‌های جانبی را نمایش یا پنهان کرد. نام برخی پنل‌ها در رابط انگلیسی است تا با مستندات و پیام‌های ابزارها هماهنگ باشد.

  • Editor: محل ویرایش سند فعال. هر فایل بازشده سند و وضعیت ذخیره‌نشده مستقل دارد.
  • Workspace/Project Explorer: مرور پوشه‌ها و فایل‌های پروژه و بازکردن فایل با دوبار کلیک.
  • Output: خروجی استاندارد، خطای استاندارد، وضعیت اجرا، مدت اجرا و کد خروج.
  • Lexical Analysis: فهرست توکن‌های تولیدشده از متن منبع.
  • Syntax Analysis: نتیجه اعتبارسنجی AST و اطلاعات خلاصه آن.
  • Errors: فهرست خطاهای قابل ناوبری.
  • Dependencies: گزارش importها و وضعیت ماژول‌ها و بسته‌ها.
  • Quality: ابزارهای Black، Ruff و pytest.
  • Terminal: نشست‌های Shell مستقل از پنل Output.
  • Git: وضعیت مخزن و عملیات کنترل نسخه.

پنل Output با ترمینال یکسان نیست: Output برای اجرای کنترل‌شده فایل/بافر و دریافت نتیجه برنامه است؛ Terminal یک Shell ماندگار برای اجرای فرمان‌های دلخواه کاربر است.

۶. ویرایشگر هوشمند

رنگ‌بندی نحوی

رنگ‌بندی با Pygments انجام می‌شود و دسته‌هایی مانند keyword، builtin، string، comment، number، function، class، operator و خطاهای lexer را از هم متمایز می‌کند. این رنگ‌بندی صرفاً نمایش بصری است و جایگزین اجرای تحلیل‌گر یا بررسی معنایی نیست.

ویرایش چندفایلی

فایل‌ها در تب‌های مستقل باز می‌شوند. هر تب وضعیت تغییرات ذخیره‌نشده خود را دارد. هنگام بستن تب یا کنارگذاشتن سند تغییرکرده، برنامه برای ذخیره، رد تغییرات یا لغو عملیات تأیید می‌گیرد. بازکردن دوباره همان مسیر از ایجاد تب تکراری جلوگیری می‌کند.

امکانات کمکی

  • شماره خطوط و برجسته‌سازی خط جاری.
  • تورفتگی خودکار پس از سربرگ بلوک‌های Python مانند if، for، while، def و class.
  • Backspace آگاه از تورفتگی و Shift+Tab برای کاهش تورفتگی خطوط.
  • بستن خودکار براکت‌ها و کوتیشن‌ها و برجسته‌سازی براکت متناظر.
  • تکمیل پایه کلمات کلیدی و built-inهای Python با Ctrl+Space؛ این قابلیت IntelliSense معنایی کامل نیست.
  • تغییر فونت و اندازه قلم، تم روشن/تاریک و Undo/Redo.
  • جست‌وجو و جایگزینی متن.

۷. تحلیل لغوی، نحوی و خطاها

تحلیل لغوی (Lexical Analysis)

تحلیل لغوی متن منبع را به Token تبدیل می‌کند. PyLex از ماژول استاندارد tokenize استفاده می‌کند. هر توکن نوع، مقدار، شماره خط و ستون شروع و پایان دارد. برای نام‌ها، تشخیص keyword با ماژول keyword و تشخیص built-inها با فضای نام builtins انجام می‌شود.

from pylex.analyzer import lexical_analysis

source = "if score >= 10:\n    print('Pass')"
for token in lexical_analysis(source):
    print(token.token_type, token.value,
          token.line, token.column,
          token.end_line, token.end_column)

نمونه دسته‌ها: KEYWORD، NAME، BUILTIN، NUMBER، STRING، OP، INDENT و NEWLINE. موقعیت ستون در داده داخلی توکن صفرمبنا است.

تحلیل نحوی (Syntax Analysis)

تحلیل نحوی بررسی می‌کند آیا توکن‌ها و عبارت‌ها مطابق دستور زبان Python کنار هم قرار گرفته‌اند یا خیر. PyLex از ast.parse استفاده می‌کند. در صورت موفقیت، درخت AST ساخته می‌شود و تعداد گره‌های آن برای گزارش خلاصه شمرده می‌شود. در صورت خطا، نوع خطا، پیام و موقعیت منبع برگردانده می‌شود.

from pylex.analyzer import syntax_analysis

result = syntax_analysis("value = 10\nprint(value)")
print(result.success)
print(result.message)
print(result.details)

تفاوت رنگ‌بندی با تحلیل

Pygments برای برجسته‌سازی بصری متن است؛ tokenize برای تولید توکن‌های واقعی زبان و ast برای اعتبارسنجی ساختار نحوی است. ممکن است متن رنگ‌بندی شود ولی از نظر نحوی نامعتبر باشد؛ همچنین رنگ‌بندی به‌تنهایی معنای متغیرها یا درستی برنامه را تضمین نمی‌کند.

پنل Errors و موقعیت‌ها

PyLex خطاهای توکن‌سازی و parser را به تشخیص‌های ساخت‌یافته تبدیل و موارد تکراری را تا حد امکان حذف می‌کند. با کلیک یا دوبار کلیک روی تشخیص، مکان‌نما به خط و ستون مربوطه می‌رود و خط منبع برجسته می‌شود. موقعیت ستون در منطق داخلی ویرایشگر صفرمبنا است؛ نمایش خطا در رابط می‌تواند به‌شکل یک‌مبنا ارائه شود. پس از تغییر کد، تحلیل را دوباره اجرا کنید تا گزارش قدیمی با متن جدید اشتباه نشود.

۸. پروژه و Workspace

Workspace یک پوشه ریشه است که زمینه مشترک فایل‌ها و پردازه‌های پروژه را مشخص می‌کند. مدل Project مسیر ریشه را resolve و نرمال می‌کند و توابعی برای ساخت مسیر نسبی، بررسی قرارگرفتن فایل در پروژه و تعیین working directory دارد.

  • پوشه پروژه را باز کنید تا درخت فایل‌ها و زیرپوشه‌ها نمایش داده شود.
  • فایل‌های متنی پشتیبانی‌شده را در تب ویرایشگر باز کنید.
  • فایل‌های باینری یا رسانه‌ای به‌جای نمایش به‌صورت متن، به برنامه پیش‌فرض سیستم سپرده می‌شوند.
  • مسیرهای اجرای پروژه از ریشه Workspace استفاده می‌کنند؛ برای فایل خارج از پروژه، پوشه همان فایل می‌تواند مبنای مسیر کاری شود.
  • مسیرهای پروژه در سرویس‌های اجرا و Git به‌صورت کنترل‌شده resolve می‌شوند.

تشخیص نوع فایل بر اساس پسوند و نگاشت داخلی انجام می‌شود؛ این تشخیص برای تجربه مرورگر فایل است و جایگزین اعتبارسنجی محتوای فایل یا اسکن امنیتی نیست.

۹. اجرا و مدیریت خروجی

کد در یک پردازه فرزند Python اجرا می‌شود تا حلقه رویداد Tkinter در زمان اجرای برنامه مسدود نشود. خروجی stdout و خطاهای stderr به‌صورت زنده خوانده و در Output نمایش داده می‌شوند. نتیجه شامل کد خروج، وضعیت و مدت اجرا است.

فایل ذخیره‌شده و بافر ذخیره‌نشده

فایل Python ذخیره‌شده و بدون تغییر از مسیر واقعی خودش اجرا می‌شود؛ این رفتار برای import کردن ماژول‌های هم‌پوشه مهم است. بافر ذخیره‌نشده در فایل موقت اجرا می‌شود، اما working directory و محیط پروژه به آن داده می‌شود. بنابراین اگر تغییرات ذخیره‌نشده روی import نسبی یا مسیر فایل اثر بگذارند، نتیجه ممکن است با اجرای نسخه ذخیره‌شده تفاوت داشته باشد.

مهلت زمانی و توقف

مهلت اجرا از Preferences قابل تنظیم است (۵، ۱۰، ۳۰ یا ۶۰ ثانیه یا Unlimited). با Stop یا Shift+F5 می‌توان پردازه اجرا و فرزندان آن را متوقف کرد. مهلت زمانی از اجرای ناخواسته طولانی جلوگیری می‌کند اما محدودیت کامل CPU، حافظه، فایل یا شبکه نیست.

نمونه مستقل سرویس اجرا

from pylex.runner import start_source

handle = start_source(
    "print('Hello from PyLex')",
    timeout=10,
)
result = handle.wait()
print(result.stdout)
print(result.stderr)
print(result.exit_code, result.status, result.duration)

API غیرهم‌زمان امکان خواندن خروجی زنده و درخواست توقف را فراهم می‌کند. API سازگاری run_source نیز برای استفاده مسدودکننده در کدهای قدیمی‌تر حفظ شده است.

۱۰. وابستگی‌ها و pip

بازرس وابستگی‌ها importهای پیدا‌شده در کد را به گروه‌هایی مانند کتابخانه استاندارد، ماژول محلی پروژه، بسته نصب‌شده و ماژول مفقود دسته‌بندی می‌کند. در صورت امکان نسخه نصب‌شده، مسیر ماژول و نام بسته توزیعی متناظر نمایش داده می‌شود. برای نمونه، نام import و نام بسته قابل نصب در pip همیشه یکسان نیستند.

بررسی ایستا نمی‌تواند همه importهای پویا، importهای شرطی یا ماژول‌هایی را که در زمان اجرا ساخته می‌شوند تشخیص دهد. در نتیجه، خطای واقعی ModuleNotFoundError هنگام اجرا همچنان مرجع نهایی برای وابستگی‌های لازم در مسیر اجرای واقعی است.

دستور نصب پیشنهادی باید با مفسر انتخاب‌شده اجرا شود. PyLex برای این منظور از الگوی python -m pip با مسیر executable همان مفسر استفاده می‌کند تا بسته اشتباهاً در Python دیگری نصب نشود.

۱۱. مفسر Python و محیط مجازی

از منوی Tools → Python Interpreter می‌توان مفسرهای موجود را بررسی و انتخاب کرد. هر نامزد با اجرای همان executable و دریافت اطلاعات نسخه، پیاده‌سازی، معماری، مسیر اجرایی و وضعیت virtual environment اعتبارسنجی می‌شود.

ترتیب انتخاب مفسر

  1. اگر برای Workspace مفسر مشخص شده باشد، همان انتخاب اولویت دارد.
  2. در غیر این صورت، PyLex محیط‌های متعارف پروژه مانند .venv، venv و env را بررسی می‌کند.
  3. در نهایت از مفسر عمومی انتخاب‌شده یا کشف‌شده استفاده می‌شود.

در Windows، جست‌وجو PATH و Python Launcher را نیز بررسی می‌کند. در سیستم‌های دیگر، مفسر جاری و نام‌های رایج در PATH بررسی می‌شوند. تشخیص venv بر پایه تفاوت sys.prefix و sys.base_prefix است، نه صرفاً وجود متغیر محیطی VIRTUAL_ENV.

ساخت محیط مجازی پروژه

از گزینه Create Project .venv برای ایجاد محیط مجازی داخل Workspace استفاده کنید. برنامه از بازنویسی پوشه هدف غیرخالی جلوگیری می‌کند و ساخت محیط را در پس‌زمینه انجام می‌دهد. پس از موفقیت، محیط برای همان Workspace انتخاب می‌شود.

python -m venv .venv
python -m pip install -r requirements.txt

فعال‌سازی shell برای اجرای برنامه از داخل PyLex ضروری نیست؛ برنامه مسیر مستقیم executable انتخاب‌شده را به سرویس اجرا، دیباگر، بازرس وابستگی و ابزارهای کیفیت می‌دهد.

نکته انتقال پروژه: پوشه‌های venv معمولاً قابل انتقال مطمئن بین رایانه‌ها نیستند، چون فایل‌های اجرایی و entry pointها ممکن است مسیر مطلق داشته باشند. پوشه .venv را در Git ثبت نکنید؛ روی سیستم مقصد آن را دوباره بسازید و وابستگی‌ها را نصب کنید.

۱۲. اشکال‌زدایی (Debugger)

دیباگر PyLex بر پایه pdb و در یک پردازه فرزند اجرا می‌شود. از Tools → Start Debugging یا کنترل‌های مربوطه برای آغاز نشست استفاده کنید. دیباگر برای مشاهده روند اجرای کد است و با اجرای عادی در Output تفاوت دارد.

قابلیت‌های اصلی

  • تعیین breakpoint عادی، شرطی و موقت.
  • Continue برای ادامه تا توقف بعدی.
  • Step Into برای ورود به فراخوانی تابع.
  • Step Over برای عبور از فراخوانی بدون ورود به آن.
  • Run Until برای ادامه تا خط مشخص.
  • Return برای اجرای تا بازگشت تابع جاری.
  • Jump برای تغییر محل اجرای خط در محدوده‌های مجاز pdb.
  • مشاهده متغیرها، آرگومان‌های تابع و stack frameها.
  • ارزیابی عبارت در زمینه frame جاری.
  • فعال/غیرفعال‌کردن، نادیده‌گرفتن یا پاک‌کردن breakpointها.

دستورات دیباگر به ورودی محدود و اعتبارسنجی‌شده تبدیل می‌شوند؛ ارزیابی عبارت‌ها همچنان کد Python را در فرایند در حال دیباگ اجرا می‌کند. از ارزیابی عبارت ناشناس یا مخرب خودداری کنید.

۱۳. ترمینال یکپارچه

از Tools → Integrated Terminal یا دکمه Terminal یک نشست Shell باز کنید. هر تب یک پردازه Shell ماندگار دارد؛ بنابراین فرمان‌هایی مانند cd، تغییر متغیر محیطی و فعال‌سازی محیط مجازی در همان نشست باقی می‌مانند.

  • Windows: PowerShell و Command Prompt؛ Git Bash در صورت نصب و شناسایی.
  • Linux/macOS: Bash، Zsh یا POSIX shellهای در دسترس.
  • ایجاد چند نشست مستقل و انتخاب Shell هنگام ساخت نشست.
  • ارسال فرمان، نمایش غیرهم‌زمان خروجی و تاریخچه Up/Down برای همان نشست.
  • Interrupt یا Ctrl+C برای قطع فرمان foreground بدون بستن لزوماً کل نشست.
  • Kill برای پایان‌دادن به پردازه Shell و فرزندان آن؛ Clear فقط نمایش را پاک می‌کند.

نشست جدید در ریشه Workspace یا پوشه فایل فعال شروع می‌شود. اگر مفسر پروژه انتخاب شده باشد، مسیر Scripts/bin آن به ابتدای PATH اضافه می‌شود و اطلاعات venv به محیط نشست منتقل می‌شود.

محدودیت مهم ترمینال: پیاده‌سازی فعلی از pipeهای ورودی/خروجی استفاده می‌کند و شبیه‌ساز کامل ConPTY/PTY نیست. فرمان‌های معمول، pip، Python و promptهای خطی پشتیبانی می‌شوند؛ برنامه‌های تمام‌صفحه TUI، ابزارهای نیازمند terminal device واقعی یا واکنش به resize ممکن است مانند ترمینال مستقل رفتار نکنند.

۱۴. Formatter، Linter و Test Explorer

پنل Tools → Formatter, Linter & Test Explorer ابزارهای کیفیت را با مفسر انتخاب‌شده Workspace اجرا می‌کند. اجرای ابزارها در پس‌زمینه است تا رابط کاربری پاسخ‌گو بماند.

Black

  • Format Buffer: متن تب فعال را به Black می‌دهد و خروجی قالب‌بندی را به همان بافر برمی‌گرداند؛ سند تغییرکرده و تا زمان ذخیره، unsaved باقی می‌ماند.
  • Format Project: قالب‌بندی فایل‌های پروژه را انجام می‌دهد. برای جلوگیری از اختلاف میان بافر حافظه و فایل دیسک، وقتی تب‌های ذخیره‌نشده وجود داشته باشند عملیات مسدود می‌شود.

Ruff

Lint Buffer و Lint Project مشکلات کد را در قالب تشخیص‌های ساخت‌یافته نمایش می‌دهند. هر تشخیص شامل rule، فایل، خط، ستون و پیام است. با دوبار کلیک روی مورد می‌توان به فایل و محل گزارش‌شده رفت.

pytest Test Explorer

Discover Tests شناسه تست‌ها (node ID) را کشف می‌کند. می‌توان کل مجموعه یا تست انتخاب‌شده را اجرا کرد؛ دوبار کلیک یا Enter روی تست کشف‌شده نیز اجرای آن را آغاز می‌کند. خروجی و وضعیت خاتمه در Tool Output نمایش داده می‌شود.

نصب ابزارها

Install Tools بسته‌های Black، Ruff و pytest را در مفسر انتخاب‌شده نصب یا به‌روزرسانی می‌کند. پیکربندی Ruff، Black و pytest در pyproject.toml قرار دارد. توقف عملیات کیفیت از کنترل Stop انجام می‌شود.

python -m black .
python -m ruff check .
python -m pytest -v

۱۵. کنترل نسخه Git

پنل Tools → Git Source Control با Git اجرایی نصب‌شده روی سیستم کار می‌کند و برای عملیات محلی به Python package یا حساب GitHub نیاز ندارد. برای عملیات remote مانند fetch/push باید remote و روش احراز هویت Git روی سیستم درست تنظیم شده باشد.

قابلیت‌ها

  • نمایش branch جاری، upstream و تعداد commitهای ahead/behind.
  • نمایش فایل‌های تغییرکرده و تفکیک تغییرات staged و unstaged.
  • مشاهده diff جداگانه برای تغییرات staged و unstaged.
  • stage/unstage یک فایل یا همه تغییرات.
  • ساخت branch و جابه‌جایی بین branchها.
  • ثبت commit از تغییرات staged با پیام الزامی.
  • Fetch، Push و Pull؛ Pull فقط با fast-forward انجام می‌شود تا merge ناخواسته ایجاد نشود.
  • مشاهده تاریخچه commitها و stash کردن working tree، شامل فایل‌های untracked.
  • Discard تغییرات با تأیید؛ حذف پوشه‌های untracked به‌صورت بازگشتی عمداً غیرفعال است.

ملاحظات ایمنی

فرمان‌ها با آرایه آرگومان اجرا می‌شوند، نه از طریق shell؛ مسیر عملیات به مخزن Workspace محدود می‌شود و promptهای تعاملی Git غیرفعال‌اند. قبل از commit، diff و فهرست staged را بازبینی کنید. Discard می‌تواند تغییرات محلی را از بین ببرد؛ از فایل‌های مهم نسخه پشتیبان داشته باشید.

۱۶. تنظیمات و ذخیره‌سازی

از View → Preferences... تنظیمات کاربری را تغییر دهید. گزینه‌های مستندشده شامل تم روشن/تاریک، خانواده و اندازه فونت، نمایش Project Explorer، مهلت اجرای کد و انتخاب مفسر هستند. ترجیحات در فایل .pylex_studio.json در پوشه Home کاربر ذخیره می‌شوند و بین اجراهای برنامه باقی می‌مانند.

ذخیره تنظیمات با نوشتن در فایل موقت هم‌پوشه، flush و fsync و سپس جایگزینی اتمیک فایل مقصد انجام می‌شود. این روش احتمال باقی‌ماندن فایل تنظیمات نیمه‌نوشته را در صورت قطع فرایند کاهش می‌دهد؛ با این حال، پشتیبان‌گیری از فایل تنظیمات در صورت اهمیت تنظیمات شخصی همچنان کار معقولی است.

تنظیمات شخصی خارج از پوشه پروژه نگهداری می‌شوند؛ بنابراین معمولاً نباید فایل تنظیمات Home را به مخزن Git پروژه اضافه کرد.

اصول طراحی

  • Separation of concerns: رابط کاربری، منطق دامنه و اجرای پردازه‌ها در ماژول‌های جدا قرار دارند.
  • Explicit context: سرویس‌های اجرا مسیر کاری، environment و executable را صریح دریافت می‌کنند.
  • Non-blocking UI: کارهای طولانی با thread/queue و پردازه فرزند مدیریت می‌شوند تا Tkinter پاسخ‌گو بماند.
  • Testability: منطق‌های خالص و سرویس‌ها تا حد امکان جدا از پنجره اصلی آزمون‌پذیرند.
  • Safe subprocess construction: فرمان‌ها با آرایه آرگومان و بدون shell=True ساخته می‌شوند.

۱۹. آزمون و CI

اجرای آزمون‌ها در سیستم محلی

python -m unittest discover -s tests -v
python -m pytest -v
python -m compileall -q pylex tests

unittest و pytest هر دو برای اجرای مجموعه آزمون‌ها پیکربندی شده‌اند. فایل pyproject.toml مسیر کشف pytest و تنظیمات Black و Ruff را نگهداری می‌کند.

کنترل کیفیت کد

python -m black --check .
python -m ruff check .

اگر ابزارها در محیط فعال نصب نیستند، ابتدا python -m pip install -r requirements-dev.txt را اجرا کنید. در پروژه‌های بزرگ می‌توان اجرای ابزارها را به مسیرهای تغییرکرده محدود کرد، اما پیش از ادغام باید مجموعه بررسی‌های CI پروژه سبز باشد.

GitHub Actions

Workflow موجود در .github/workflows/tests.yml تست‌ها را در ماتریس Windows و Ubuntu و Python 3.10، 3.11 و 3.13 اجرا می‌کند. بررسی Black در job مشخص CI نیز اجرا می‌شود. نتیجه workflow در تب Actions مخزن قابل مشاهده است.

راهنمای افزودن آزمون

  • برای هر رفتار جدید یک تست موفق و برای ورودی نامعتبر یک تست خطا در نظر بگیرید.
  • برای عملیات فایل و پردازه، مسیر موقت و پاک‌سازی منابع را بررسی کنید.
  • برای عملیات وابسته به سیستم‌عامل، تفاوت Windows و POSIX را در طراحی تست لحاظ کنید.
  • از وابستگی آزمون‌ها به وضعیت واقعی حساب کاربری، مسیر شخصی یا تنظیمات محلی پرهیز کنید.

۲۰. امنیت و محدودیت‌ها

هشدار امنیتی: اجرای کد در PyLex Studio Sandbox امنیتی نیست. برنامه با مجوزهای کاربر جاری سیستم اجرا می‌شود؛ کد می‌تواند به فایل‌ها، شبکه و منابعی دسترسی پیدا کند که همان کاربر مجاز به استفاده از آن‌هاست.
  • Timeout فقط مدت اجرا را محدود می‌کند؛ محدودکننده جامع منابع یا مرز امنیتی نیست.
  • توقف درخت پردازه تلاش می‌کند پردازه اصلی و فرزندان آن را خاتمه دهد؛ این ویژگی معادل sandbox نیست.
  • ترمینال یک Shell واقعی سیستم را اجرا می‌کند؛ فرمان‌ها با سطح دسترسی کاربر انجام می‌شوند.
  • فرمان‌های Git با آرایه آرگومان و در محدوده Workspace اجرا می‌شوند؛ بااین‌حال، عملیات destructive همچنان نیازمند دقت کاربر است.
  • Dependency inspection ایستا است و تمام importهای پویا را کشف نمی‌کند.
  • پیشنهاد تکمیل کد، semantic IntelliSense یا بررسی کامل نوع‌ها نیست.
  • ترمینال فعلی PTY/ConPTY کامل نیست.

برای اجرای امن کد ناشناس، به یک sandbox واقعی مبتنی بر سیستم‌عامل یا ماشین مجازی محدودشده، کاربر کم‌دسترسی، محدودیت CPU و حافظه، کنترل فایل‌سیستم و سیاست شبکه نیاز است. تا زمان پیاده‌سازی و آزمون چنین مرزی، کد ناشناس را اجرا نکنید.

۲۱. عیب‌یابی متداول

برنامه با خطای Tkinter اجرا نمی‌شود

بررسی کنید نصب Python شما Tkinter را دارد. در Linux بسته Tkinter توزیع را نصب کنید؛ در Windows از نصب رسمی Python با مؤلفه Tcl/Tk استفاده کنید. سپس python -m tkinter را برای بررسی وجود پنجره آزمایشی اجرا کنید.

Pygments نصب نیست یا رنگ‌بندی انجام نمی‌شود

python -m pip install "Pygments>=2.18,<3.0"
python -c "import pygments; print(pygments.__version__)"

دستور را با همان Python محیطی اجرا کنید که برنامه را با آن شروع می‌کنید.

بسته در برنامه پیدا نمی‌شود

از Tools → Python Interpreter executable انتخاب‌شده را بررسی کنید. سپس از Dependency Inspector وضعیت ماژول را ببینید و نصب را با همان مفسر انجام دهید. فعال‌بودن venv در ترمینال خارجی لزوماً به این معنا نیست که PyLex همان مفسر را انتخاب کرده است.

import محلی پروژه کار نمی‌کند

پوشه ریشه پروژه را به‌عنوان Workspace باز کنید. برای فایل ذخیره‌شده، مسیر واقعی فایل و ریشه پروژه در اجرای برنامه نقش دارند. برای تغییرات ذخیره‌نشده، فایل موقت اجرا می‌شود؛ اگر ساختار import پیچیده است، فایل را ذخیره و دوباره اجرا کنید.

ترمینال فرمان تعاملی یا تمام‌صفحه را درست اجرا نمی‌کند

ترمینال PyLex از pipe استفاده می‌کند و PTY کامل نیست. برای ابزارهای تمام‌صفحه، رابط‌های تعاملی پیچیده یا نیازمند terminal resize از Windows Terminal، ترمینال سیستم یا ترمینال مستقل استفاده کنید.

Git fetch/push احراز هویت نمی‌شود

ابتدا در ترمینال مستقل بررسی کنید Git نصب و remote درست تنظیم شده است و credential manager یا SSH key معتبر است. پنل PyLex promptهای تعاملی را غیرفعال می‌کند؛ بنابراین ابتدا احراز هویت Git را خارج از برنامه تکمیل کنید.

اجرای کد متوقف نمی‌شود یا timeout رخ می‌دهد

وضعیت خروجی و timeout انتخاب‌شده را بررسی کنید. در صورت نیاز Stop یا Shift+F5 را بزنید. timeout را فقط برای برنامه‌های مورد اعتماد و زمانی که واقعاً لازم است روی Unlimited قرار دهید.

تنظیمات پس از اجرا باقی نمی‌مانند

مطمئن شوید پوشه Home کاربر قابل نوشتن است و فایل .pylex_studio.json توسط ابزار همگام‌سازی یا آنتی‌ویروس قفل نشده است. در صورت خرابی تنظیمات، قبل از هر تغییری از فایل نسخه پشتیبان بگیرید.

۲۲. مشارکت و گردش توسعه

  1. مخزن را fork یا clone کنید و یک branch با نام مشخص برای تغییر بسازید.
  2. تغییر را محدود به یک موضوع نگه دارید و مستندات و تست متناظر را به‌روزرسانی کنید.
  3. آزمون‌های unittest و pytest و بررسی‌های Black/Ruff را اجرا کنید.
  4. تغییرات را با Git diff بازبینی کنید؛ فایل‌های محیط مجازی، تنظیمات شخصی و خروجی‌های موقت را commit نکنید.
  5. Pull Request با توضیح هدف، پیاده‌سازی، تست‌ها و اثرات کاربری بسازید.
  6. پیش از ادغام، CI و تست دستی رابط در Windows را بررسی کنید.
  7. برای انتشار نسخه، ابتدا تغییرات main و Tag نسخه را هماهنگ کنید و سپس GitHub Release را منتشر کنید.

  • ترمینال مبتنی بر PTY/ConPTY کامل برای برنامه‌های تمام‌صفحه.
  • بسته‌بندی و انتشار نصب‌کننده‌های بومی برای سیستم‌عامل‌های هدف.
  • Sandbox واقعی و قابل ارزیابی برای اجرای کد غیرقابل اعتماد.
  • بهبود دسترس‌پذیری، آزمون‌های GUI و پوشش سناریوهای پیچیده.

اولویت هر قابلیت باید پس از بررسی نیاز کاربران، هزینه نگهداری، ریسک امنیتی و امکان آزمون‌پذیری تعیین شود.

۲۵. آموزش عملی: ساخت و اجرای اولین پروژه

این تمرین از یک پوشه خالی شروع می‌شود و مسیر کامل کار با PyLex Studio را نشان می‌دهد. هدف این است که فقط دکمه‌ها را نشناسید، بلکه بدانید هر مرحله چه اثری روی پروژه و محیط Python دارد.

گام ۱: ساخت پوشه و بازکردن Workspace

در File Explorer یک پوشه مانند hello_pylex بسازید. در PyLex Studio گزینه File → Open Workspace... یا دکمه Open Workspace را انتخاب کنید و همان پوشه را باز کنید. پوشه در Project Explorer سمت چپ دیده می‌شود. Workspace به برنامه می‌گوید ریشه پروژه کجاست؛ مسیر کاری، بررسی importها، ترمینال، ابزارهای کیفیت و پنل Git از این زمینه استفاده می‌کنند.

گام ۲: ساخت فایل Python

از File → New یا Ctrl+N یک سند جدید بسازید. کد زیر را وارد کنید:

def greet(name):
    message = f"Hello, {name}!"
    return message

if __name__ == "__main__":
    print(greet("PyLex Studio"))

با File → Save یا Ctrl+S فایل را در پوشه Workspace با نام main.py ذخیره کنید. عنوان تب نام فایل را نشان می‌دهد؛ نشان تغییر کنار تب یعنی هنوز تغییر ذخیره‌نشده دارید. تا زمانی که ذخیره نکرده‌اید، محتوای تب با فایل روی دیسک یکسان نیست.

گام ۳: شناخت رنگ‌ها و ابزارهای ویرایش

کلمات کلیدی، رشته‌ها، اعداد، commentها و نام تابع‌ها با رنگ‌های متفاوت مشخص می‌شوند. این رنگ‌ها فقط برای خوانایی‌اند. برای تکمیل کلمات پایه Python، مکان‌نما را بعد از چند حرف نام قرار دهید و Ctrl+Space را بزنید. برای کامنت‌کردن چند خط، بلوک را انتخاب و Ctrl+/ را فشار دهید. Ctrl+D خط/انتخاب را تکثیر می‌کند و Alt+Up/Down خط جاری را جابه‌جا می‌کند.

گام ۴: تحلیل کد پیش از اجرا

از Tools → Analyze All یا F6 استفاده کنید. تب Lexical Analysis توکن‌های متن را نمایش می‌دهد؛ Syntax Analysis نتیجه parse شدن متن به AST را نشان می‌دهد؛ Errors خطاهای قابل ناوبری را فهرست می‌کند. برای مشاهده جداگانه هر مرحله از Tools → Lexical Analysis یا Tools → Syntax Analysis استفاده کنید.

برای دیدن نحوه گزارش خطا، موقتاً دونقطه بعد از if را حذف کنید و دوباره Analyze All بزنید. در Errors نوع خطا، شماره خط، ستون، پیام و خط منبع را می‌بینید. روی ردیف خطا کلیک یا دوبار کلیک کنید تا مکان‌نما به محل گزارش‌شده برود. پس از اصلاح متن، تحلیل را دوباره اجرا کنید؛ تغییر کد باعث می‌شود تشخیص‌های قبلی منقضی شوند.

گام ۵: اجرای برنامه

با F5 یا دکمه Run برنامه را اجرا کنید. تب Output به‌صورت خودکار نمایش داده می‌شود. stdout و stderr با رنگ‌های متفاوت، همراه با پیام‌های سیستمی نشان داده می‌شوند. در پایان، وضعیت اجرا، کد خروج و مدت اجرا را بررسی کنید. کد خروج صفر معمولاً نشان‌دهنده پایان موفق برنامه است؛ مقدار غیرصفر معمولاً به خطای برنامه یا شکست پردازه اشاره دارد.

برای توقف برنامه‌ای که منتظر ورودی یا در حلقه بی‌نهایت است از Force Stop Run یا Shift+F5 استفاده کنید. این عمل پردازه اجرا را خاتمه می‌دهد و با پاک‌کردن متن Output فرق دارد. دکمه Clear Output فقط نمایش خروجی را پاک می‌کند. برای نگهداری نتیجه از Save Output استفاده کنید.

گام ۶: انتخاب Python مناسب

از Tools → Python Interpreter... یا دکمه Python، فهرست مفسرهای کشف‌شده را باز کنید. نسخه و مسیر executable را بررسی کنید. اگر Workspace محیط .venv دارد، آن را انتخاب کنید یا از گزینه ساخت Project .venv استفاده کنید. پس از انتخاب، اجرای برنامه، دیباگر، Dependency Inspector و ابزارهای کیفیت باید از همان executable استفاده کنند.

گام ۷: بررسی وابستگی‌ها

برای پروژه‌ای که از کتابخانه بیرونی استفاده می‌کند، تب Dependencies را باز و Scan Current File را اجرا کنید. ستون Import نام استفاده‌شده در کد، Status وضعیت تشخیص، Package / Source نام توزیع یا منبع و Version نسخه نصب‌شده را نشان می‌دهد. اگر بسته‌ای مفقود است، مطمئن شوید مفسر انتخابی همان محیطی است که می‌خواهید و سپس دستور نصب پیشنهادی را با همان Python اجرا کنید.

گام ۸: دیباگ در صورت نیاز

در خط موردنظر مکان‌نما را قرار دهید و F9 را برای breakpoint بزنید. با Ctrl+F5 یا Tools → Start Debugging اجرای دیباگ را شروع کنید. وقتی اجرا متوقف شد، Continue با Ctrl+F10، Step Into با F11 و Step Over با F10 قابل استفاده‌اند. Variables، Arguments و Stack وضعیت frame جاری را نمایش می‌دهند. پس از پایان کار Stop Debugging را بزنید تا نشست دیباگر بسته شود.

گام ۹: بررسی کیفیت و تست

تب Quality را باز کنید. ابتدا Discover Tests را برای کشف تست‌های pytest اجرا کنید. سپس Ruff را برای یافتن مشکلات کد اجرا کنید و در صورت نیاز Black را روی بافر فعال اجرا کنید. قالب‌بندی بافر فعلی نتیجه را در همان تب اعمال می‌کند؛ برای نگهداری آن Ctrl+S بزنید. پیش از Format Project همه تب‌های تغییرکرده را ذخیره یا ببندید؛ برنامه این شرط را برای جلوگیری از اختلاف میان حافظه و دیسک اعمال می‌کند.

گام ۱۰: ذخیره و کنترل نسخه

اگر پوشه پروژه مخزن Git باشد، تب Git وضعیت تغییرات را نشان می‌دهد. ابتدا diff را بررسی کنید، سپس فایل‌های موردنظر را stage کنید، پیام commit بنویسید و Commit را اجرا کنید. Fetch اطلاعات remote را می‌گیرد؛ Push commitهای محلی را ارسال می‌کند؛ Pull فقط در حالت fast-forward انجام می‌شود. پیش از Pull، تغییرات محلی را ذخیره یا commit کنید تا Git مجبور به ادغام خودکار نشود.

نتیجه تمرین: اکنون یک پروژه کوچک دارید که از Workspace و ویرایش چندفایلی تا تحلیل، اجرا، دیباگ، بررسی وابستگی، کیفیت و Git را در یک گردش‌کار تجربه کرده است.

۲۶. سناریوهای رایج و گردش‌کارها

بازکردن پروژه‌ای که از قبل وجود دارد

  1. File → Open Workspace را انتخاب کنید و پوشه ریشه را باز کنید.
  2. درخت فایل را با دکمه Refresh به‌روز کنید.
  3. روی فایل دوبار کلیک کنید تا در تب جدید باز شود.
  4. اگر پروژه محیط مجازی دارد، مطمئن شوید نام آن در .venv، venv یا env قرار دارد یا مفسر را دستی انتخاب کنید.
  5. پیش از اجرا، مسیر کاری و Dependencies را بررسی کنید.

رفع خطای SyntaxError یا IndentationError

  1. Analyze All را اجرا کنید.
  2. در تب Errors ردیف خطا را انتخاب کنید.
  3. به متن خط و ستون گزارش‌شده توجه کنید؛ محل خطا گاهی جایی است که parser دیگر نمی‌تواند ساختار را ادامه دهد، نه لزوماً اولین نویسه اشتباه.
  4. براکت‌ها، کوتیشن‌ها، دونقطه و تورفتگی بلوک را بررسی کنید.
  5. پس از اصلاح دوباره Analyze All و سپس Run را اجرا کنید.

حل ModuleNotFoundError

  1. از متن خطا نام ماژول import‌شده را بردارید.
  2. Tools → Python Interpreter را باز کنید و مسیر Python فعال را کنترل کنید.
  3. در Dependencies روی Scan Current File بزنید.
  4. اگر ماژول بخشی از پروژه نیست و در محیط نصب نشده، از Copy Python Install Command یا ترمینال همان محیط برای نصب بسته درست استفاده کنید.
  5. دوباره اجرا کنید. نام import ممکن است با نام بسته pip متفاوت باشد؛ برای مثال yaml معمولاً از توزیع PyYAML می‌آید.

اجرای برنامه‌ای که ورودی می‌خواهد

پنل Output از ورودی استاندارد تعاملی برنامه‌های Python، از جمله تابع input() و promptهای بدون newline، پشتیبانی می‌کند. پاسخ را در ناحیه ورودی Output تایپ و با Enter ارسال کنید. برای اجرای فرمان‌های Shell، مدیریت نشست‌های ماندگار یا برنامه‌هایی که به TTY کامل و رابط تمام‌صفحه نیاز دارند، از Terminal یا ترمینال مستقل سیستم استفاده کنید.

قالب‌بندی بدون از دست دادن تغییرات

برای فرمت‌کردن فقط تب جاری از Format Buffer استفاده کنید و نتیجه را بازبینی و ذخیره کنید. برای Format Project ابتدا همه تب‌های dirty را ذخیره کنید. پروژه را پیش از قالب‌بندی گروهی commit کنید تا بتوانید تغییرات Black را با diff بازبینی یا در صورت لزوم برگردانید.

بررسی تغییرات پیش از Commit

  1. Git → Refresh/Status را به‌روزرسانی کنید.
  2. فایل تغییرکرده را انتخاب کنید و diff unstaged را ببینید.
  3. فقط فایل‌هایی را stage کنید که باید وارد commit شوند.
  4. diff staged را جداگانه بازبینی کنید؛ staged و unstaged دو مجموعه متفاوت‌اند.
  5. پیام معنادار بنویسید و Commit کنید.
  6. پس از بررسی branch و remote، در صورت نیاز Push کنید.

۲۹. انتخاب مفسر و محیط اجرا در عمل

انتخاب Python فقط یک تنظیم ظاهری نیست؛ مشخص می‌کند کدام نسخه Python و کدام مجموعه بسته‌ها برای اجرای برنامه و ابزارهای توسعه استفاده شود.

ترتیب اولویت

  1. مفسر صریح ذخیره‌شده برای همان Workspace، اگر معتبر باشد.
  2. محیط مجازی شناخته‌شده در ریشه پروژه، به‌ترتیب پوشه‌های .venv، venv و env.
  3. مفسر سراسری انتخاب‌شده در Preferences.
  4. مفسر Python جاری برنامه در صورت نبود تنظیم دیگر.

چه زمانی مفسر پروژه را انتخاب کنیم؟

وقتی دو پروژه نسخه Python یا dependencyهای متفاوت دارند، برای هر Workspace مفسر جدا انتخاب کنید. انتخاب سراسری برای پروژه‌هایی مناسب است که از یک محیط مشترک استفاده می‌کنند. در صورت جابه‌جایی پوشه پروژه یا حذف venv، مسیر ذخیره‌شده ممکن است دیگر معتبر نباشد؛ مفسر را دوباره انتخاب کنید.

چرا pip نصب کرده‌ام اما برنامه ماژول را پیدا نمی‌کند؟

اغلب علت این است که pip متعلق به Python دیگری بوده است. در ترمینال از python -m pip show package-name استفاده کنید، اما ابتدا مطمئن شوید فرمان python همان executable انتخاب‌شده در PyLex است. روش قطعی‌تر، اجرای مسیر کامل Python انتخاب‌شده به شکل FULL_PATH_TO_PYTHON -m pip install package-name است. PyLex نیز دستور نصب را با executable انتخاب‌شده می‌سازد.

چرا پس از کپی پروژه باید venv را دوباره بسازم؟

venv مسیرهای داخلی و اسکریپت‌هایی دارد که ممکن است به محل Python اصلی یا مسیر محیط قبلی وابسته باشند. مخزن باید کد و فهرست dependencyها را نگه دارد، نه کپی محیط نصب‌شده روی یک رایانه. محیط را در مقصد دوباره بسازید و dependencyها را نصب کنید.

۳۰. پرسش‌های پرتکرار

آیا PyLex Studio فقط یک ویرایشگر متن است؟

خیر. علاوه بر ویرایشگر، ابزار تحلیل لغوی و نحوی، اجرای برنامه، مدیریت مفسر و محیط مجازی، بررسی وابستگی، دیباگر pdb، ترمینال، Black، Ruff، pytest و Git دارد. بااین‌حال، بعضی قابلیت‌های پیشرفته IDEهای بزرگ مانند تحلیل معنایی کامل یا LSP در دامنه نسخه 2.0.2 نیستند.

آیا می‌توان پروژه‌ای با چند فایل Python اجرا کرد؟

بله. پوشه ریشه را به‌عنوان Workspace باز کنید و فایل اصلی را اجرا کنید. فایل ذخیره‌شده از مسیر واقعی خود اجرا می‌شود و Workspace مسیر کاری و زمینه import را فراهم می‌کند. ساختار package و importها باید مطابق قواعد Python باشد.

آیا PyLex همه خطاهای برنامه را قبل از اجرا پیدا می‌کند؟

خیر. تحلیل لغوی و نحوی خطاهای ساختاری را بررسی می‌کند؛ Ruff مجموعه‌ای از مشکلات استاتیک را تشخیص می‌دهد. خطاهای منطقی، داده‌ای، شبکه‌ای، محیطی و بسیاری از خطاهای زمان اجرا فقط هنگام اجرای برنامه یا تست مشخص می‌شوند.

آیا می‌توان برنامه را با ورودی تعاملی اجرا کرد؟

برای برنامه‌های Python که از input() استفاده می‌کنند، می‌توانید پاسخ را مستقیماً در Output وارد کنید؛ promptهای بدون newline نیز به‌صورت زنده نمایش داده می‌شوند. Terminal برای فرمان‌های Shell، نشست‌های ماندگار و اجرای فایل فعال در زمینه Workspace و مفسر انتخاب‌شده است. برنامه‌هایی که به TTY کامل نیاز دارند ممکن است به ترمینال سیستم احتیاج داشته باشند.

آیا اجرای برنامه ایمن و محدودشده است؟

خیر. پردازه با مجوز کاربر جاری اجرا می‌شود. فایل‌ها، شبکه و منابعی که کاربر به آن‌ها دسترسی دارد ممکن است در دسترس کد باشند. هرگز کد ناشناس را صرفاً به دلیل اجرا شدن در PyLex قابل اعتماد فرض نکنید.

آیا Git باید جداگانه نصب شود؟

بله. پنل Git به executable واقعی Git وابسته است. اگر Git در PATH نباشد، پنل نمی‌تواند عملیات مخزن را انجام دهد. همچنین احراز هویت remote باید از قبل در Git سیستم تنظیم شده باشد.

چرا Format Project در حضور تب تغییرکرده اجرا نمی‌شود؟

چون Black فایل‌های روی دیسک را قالب‌بندی می‌کند و ممکن است با متن ذخیره‌نشده در تب‌ها تعارض ایجاد کند. تب‌های تغییرکرده را ذخیره یا ببندید و دوباره عملیات را اجرا کنید.

چرا پنل Git چیزی نشان نمی‌دهد؟

Workspace باید داخل یک مخزن Git باشد؛ یعنی خود پوشه یا یکی از والدهای آن باید مخزن معتبر داشته باشد. اگر Git نصب نیست یا پوشه انتخاب‌شده بیرون از مخزن است، ابتدا مخزن را ایجاد یا پوشه ریشه درست را باز کنید.

کجا باید خطا را گزارش کنم؟

ابتدا نسخه برنامه، سیستم‌عامل، نسخه Python انتخاب‌شده و مراحل بازتولید خطا را ثبت کنید. اگر خطا traceback دارد، متن کامل آن را نگه دارید. سپس در مخزن GitHub پروژه یک Issue با عنوان روشن، مراحل بازتولید، نتیجه مورد انتظار و نتیجه واقعی ایجاد کنید. پیش از انتشار اطلاعات شخصی، مسیرهای خصوصی، tokenها و محتوای محرمانه را از گزارش حذف کنید.

معماری ماژولار برنامه در نسخه 2.2.0

هدف نسخه 2.2.0 انتقال تدریجی مالکیت وضعیت و چرخه عمر از پنجره اصلی به Controllerهای مستقل است؛ بدون بازطراحی رابط و بدون تغییر قراردادهای رفتاری Run، Debug، Workspace یا تب‌های ویرایشگر. پنجره PyLexApp نقش Composition Root و لایه نمایش را حفظ می‌کند: ساخت ویجت‌ها، نمایش پیام‌ها، زمان‌بندی polling و به‌روزرسانی وضعیت رابط همچنان در UI انجام می‌شود.

مرزهای مسئولیت

  • WorkspaceController در pylex.controllers.workspace: بازکردن، بازیابی و بستن مدل Project و تعیین context پروژه برای فایل‌ها را مدیریت می‌کند. نمایش درخت فایل، انتخاب پوشه و پیام‌های خطا در UI باقی می‌ماند.
  • DocumentController در pylex.controllers.documents: ثبت و حذف سند، انتخاب و بازیابی ویرایشگر فعال، جست‌وجوی سند بر اساس مسیر و وضعیت dirty را بدون وابستگی به Tk مدیریت می‌کند. ساخت تب و ویجت ویرایشگر همچنان مسئولیت UI است.
  • ExecutionController در pylex.controllers.execution: مالک handle اجرای فعال است، اجرای هم‌زمان ناخواسته را رد می‌کند و عملیات stop و finish را هماهنگ می‌سازد. ایجاد process و context مفسر همچنان از طریق ExecutionService انجام می‌شود؛ نمایش خروجی و polling در UI باقی می‌ماند.
  • DebuggerController در pylex.controllers.debugger: شروع session، جلوگیری از شروع session تکراری، توقف، بستن و پاک‌سازی چرخه عمر Debugger را مدیریت می‌کند. فرمان‌های pdb و تعاملات کاربر از طریق UI و API موجود session ادامه دارند.

جهت وابستگی‌ها

لایه UI Controllerها را فراخوانی می‌کند؛ Controllerها به مدل‌های Core و Serviceهای موجود وابسته‌اند و هیچ‌کدام ویجت Tkinter نمی‌سازند یا پنجره گرافیکی را import نمی‌کنند. ExecutionController و DebuggerController از ExecutionService استفاده می‌کنند و مسئولیت ساخت فرایند را دوباره پیاده‌سازی نمی‌کنند.

سازگاری و مهاجرت تدریجی

ویژگی‌های دسترسی فعلی PyLexApp مانند project، documents، editor، execution و debug_session به‌صورت property به state متعلق به Controllerها متصل هستند. این لایه سازگاری از بازنویسی یک‌باره تمام callbackها جلوگیری می‌کند و امکان انتقال مرحله‌ای بخش‌های باقی‌مانده را فراهم می‌سازد. ساختار ظاهری، تم‌ها، منوها، میانبرها، پنل‌ها و رفتار تب‌ها در این مرحله هدف تغییر نیستند.

اعتبارسنجی

آزمون‌های مستقل tests/test_controllers.py چرخه عمر Controllerها را بدون ساخت پنجره Tk بررسی می‌کنند. آزمون‌های یکپارچگی موجود برای اجرای فایل واقعی، مسیر کاری Workspace، PYTHONPATH، ورودی استاندارد، ترمینال و Debugger حفظ می‌شوند. ماتریس CI همچنان Windows و Ubuntu با Python 3.10، 3.11 و 3.13 را پوشش می‌دهد؛ Ruff و Black نیز کنترل کیفیت کد را انجام می‌دهند.

نسخه 2.2.0 منتشر شده و معماری آن Controllerهای مستقل برای Workspace، Documents، Execution و Debugger را معرفی می‌کند.

معماری ماژولار رابط برنامه در نسخه 2.3.0

در نسخه منتشرشده 2.3.0، پیاده‌سازی بزرگ پنجره اصلی به چند ماژول مسئولیت‌محور تقسیم شد. هدف این تغییر، آسان‌تر شدن نگهداری و توسعه مستقل بخش‌هاست؛ نه بازطراحی رابط کاربری. کلاس PyLexApp همچنان پنجره اصلی و Composition Root است و ساخت ویجت‌ها، callbackها، زمان‌بندی رویدادها و هماهنگی میان بخش‌ها را حفظ می‌کند.

تقسیم مسئولیت‌ها

  • ToolbarMixin در pylex.app_parts.toolbar: منوهای اصلی، toolbar و کنترل‌های فرمان.
  • ShellMixin در pylex.app_parts.shell: لوگو، Activity Bar، چیدمان Workspace و اتصال اجزای اصلی پوسته.
  • PanelsMixin در pylex.app_parts.panels: status bar، پنل‌های Output و Analysis، خطاها، ترمینال، کیفیت و وابستگی‌ها.
  • WorkspaceMixin در pylex.app_parts.workspace: باز و بسته‌کردن Workspace، فایل‌ها، درخت پروژه، مسیرهای اخیر و عملیات فایل/پوشه.
  • DocumentsMixin در pylex.app_parts.documents: تب‌ها، سند فعال، ایجاد/بازکردن/ذخیره فایل و تنظیمات نمایش ویرایشگر.
  • AnalysisMixin در pylex.app_parts.analysis: تحلیل لغوی و نحوی و پاک‌سازی نتایج.
  • ExecutionMixin و DebuggerMixin: اجرای برنامه، خروجی و ورودی تعاملی، و چرخه فرمان‌های Debugger.
  • PreferencesMixin در pylex.app_parts.preferences: تنظیمات، پنجره‌های ترجیحات، تغییر تم و تنظیمات رابط؛ مالکیت ساخت و بستن پنجره اصلی در PyLexApp باقی می‌ماند.

مرز معماری و سازگاری

ماژول‌های جدید به شکل mixinهای بدون state مستقل ترکیب می‌شوند و از طریق self به همان رابط داخلی موجود دسترسی دارند. در این مرحله نام callbackها و قراردادهای متصل به ویجت‌ها تغییر نکرده‌اند؛ این روش، استخراج کد را بدون بازنویسی رفتارهای رابط انجام می‌دهد. Controllerهای مستقل معرفی‌شده در نسخه 2.2.0 همچنان مالک چرخه عمر Workspace، Documents، Execution و Debugger باقی می‌مانند.

وابستگی‌ها و اعتبارسنجی

requirements.txt فقط بسته‌های زمان اجرا را نگه می‌دارد. ابزارهای توسعه و کنترل کیفیت مانند pytest، Black و Ruff در requirements-dev.txt قرار دارند. تست‌های معماری ترکیب مسئولیت‌ها را بررسی می‌کنند و تست GUI در محیط دارای نمایشگر، راه‌اندازی واقعی پنجره و وجود اجزای اصلی را کنترل می‌کند؛ در runnerهای headless این تست GUI با وضعیت skip مشخص می‌شود. ماتریس Windows و Ubuntu با Python 3.10، 3.11 و 3.13 و کنترل‌های Ruff و Black حفظ می‌شود.

نسخه 2.3.0 منتشر شده است و این بخش معماری ماژولار رابط برنامه در همان نسخه را مستند می‌کند.

بهینه‌سازی بارگذاری و فایل‌های حجیم در نسخه 2.3.1

برای جلوگیری از مسدود شدن رابط گرافیکی هنگام باز کردن فایل‌های متنی بزرگ، خواندن فایل‌هایی با اندازه حداقل 512 کیلوبایت در worker پس‌زمینه انجام می‌شود. نتیجه فقط از طریق صف به نخ اصلی رابط تحویل داده می‌شود؛ تمام عملیات ویجت‌های Tkinter همچنان در نخ رابط انجام می‌گیرند.

حالت فایل حجیم

  • محتوا در قطعه‌های محدود درج می‌شود تا event loop فرصت پردازش رویدادها و repaint را داشته باشد.
  • برای سندهای بزرگ، Syntax Highlighting کامل، اسکن سراسری براکت‌ها و تولید انبوه شماره خطوط کنار گذاشته می‌شود تا ویرایش و پیمایش پاسخ‌گوتر بماند.
  • برای فایل‌های معمولی، رفتار ویرایشگر و نمایش شماره خطوط حفظ می‌شود.
  • Lexer بر اساس پسوند فایل انتخاب می‌شود؛ بنابراین JSON دیگر با PythonLexer پردازش نمی‌شود.

حالت فایل حجیم یک مصالحه عملکردی است: برای سندهای بزرگ، شماره خطوط و رنگ‌آمیزی نحوی موقتاً غیرفعال‌اند. این حالت محتوای فایل را تغییر نمی‌دهد و محدودیتی برای ذخیره‌سازی ایجاد نمی‌کند.

پاسخ‌گویی و پایداری ویرایشگر در نسخه منتشرشده 2.4.0

نسخه 2.4.0 کارهای سنگین رنگ‌آمیزی نحوی را از نخ رابط Tkinter خارج می‌کند و به‌روزرسانی‌های پرتکرار ویرایشگر را تجمیع می‌کند. این قابلیت‌ها همراه با بهبود بارگذاری Workspace و ذخیره‌سازی در نسخه 2.4.0 منتشر شده‌اند.

تحلیل نحوی و رنگ‌آمیزی پس‌زمینه‌ای

  • ساخت بازه‌های توکن Pygments در worker پس‌زمینه انجام می‌شود؛ worker به ویجت‌های Tkinter دسترسی ندارد.
  • نتیجه از طریق صف به نخ اصلی رابط منتقل می‌شود و tagهای رنگ‌آمیزی در batchهای محدود اعمال می‌شوند.
  • با تغییر متن، تعویض سند یا نابودی ویرایشگر، کار قبلی لغو یا نتیجه قدیمی نادیده گرفته می‌شود تا محتوای کهنه روی سند جدید اعمال نشود.
  • لغو در حین پیمایش توکن‌ها بررسی می‌شود تا کار منسوخ‌شده بی‌دلیل ادامه پیدا نکند.

کاهش به‌روزرسانی‌های تکراری

  • به‌روزرسانی gutter شماره خطوط با زمان‌بندی تجمیعی انجام می‌شود.
  • محاسبه براکت متناظر با تأخیر کوتاه انجام می‌شود تا حرکت سریع مکان‌نما محاسبات غیرضروری ایجاد نکند.
  • در زمان نابودی ویرایشگر، callbackها و jobهای زمان‌بندی‌شده پاک‌سازی می‌شوند تا از اجرای callback روی widget ازبین‌رفته جلوگیری شود.
  • نشانگرهای encoding و newline در status bar از metadata سند خوانده می‌شوند و برای هر حرکت مکان‌نما کل متن ویرایشگر دوباره پیمایش نمی‌شود.

کنترل کیفیت

CI روی Windows و Ubuntu و Pythonهای 3.10، 3.11 و 3.13 اجرا می‌شود. در ماتریس نسخه 2.4.0، pytest و compileall و همچنین Black و Ruff در هر شش ترکیب اجرا می‌شوند. تستی که به نمایشگر واقعی Tk نیاز دارد در runnerهای headless با وضعیت skip گزارش می‌شود؛ این skip به معنی اجرای تست GUI در آن محیط نیست.

این قابلیت‌ها در نسخه 2.4.0 معرفی شده‌اند و به‌عنوان بخشی از پایه پایداری نسخه 2.4.1 حفظ شده‌اند. آخرین نسخه پایدار فعلی 2.4.1 است.

تحلیل پس‌زمینه‌ای و پاسخ‌گویی بیشتر رابط در نسخه 2.4.1

در تغییرات نسخه 2.4.1، تحلیل لغوی، تحلیل نحوی و جمع‌آوری Diagnosticها روی worker پس‌زمینه اجرا می‌شوند تا پردازش فایل‌های بزرگ، event loop رابط Tkinter را متوقف نکند. worker فقط با snapshot متن کار می‌کند و هیچ ویجت Tkinter را لمس نمی‌کند؛ نمایش گزارش‌ها و ساخت ردیف‌های خطا صرفاً در نخ اصلی انجام می‌شود.

چرخه عمر و جلوگیری از نتیجه منسوخ

  • هر درخواست تحلیل شناسه نسل و رویداد لغو مستقل دارد؛ درخواست تازه، درخواست قبلی را بی‌اعتبار می‌کند.
  • با تغییر متن سند فعال، جابه‌جایی میان تب‌ها، پاک‌کردن نتایج یا بستن برنامه، کار قبلی لغو می‌شود.
  • نتیجه فقط وقتی نمایش داده می‌شود که همان ویرایشگر هنوز باز و فعال باشد و محتوای فعلی دقیقاً با snapshot زمان شروع تحلیل مطابقت داشته باشد.
  • نتایج worker از صف thread-safe عبور می‌کنند و تمام تغییرات ویجت‌ها در نخ رابط انجام می‌شوند.

تطبیق براکت‌ها

محاسبه براکت متناظر پس از debounce کوتاه در worker انجام می‌شود. اسکن در طول پیمایش توکن‌ها و delimiterها نقطه‌های بررسی لغو دارد؛ اگر مکان‌نما یا متن تغییر کند، نتیجه قبلی نادیده گرفته می‌شود و روی سند جدید اعمال نخواهد شد.

آزمون و اعتبارسنجی

آزمون‌های مستقل برای حالت‌های lexical، syntax و all، گزارش خطای نحوی و لغو تحلیل و تطبیق براکت اضافه شده‌اند. CI شاخه توسعه با موفقیت هر شش ترکیب Windows و Ubuntu با Python 3.10، 3.11 و 3.13 را گذرانده است: 169 تست موفق، 1 تست skip و 12 subtest موفق؛ compileall، Black و Ruff نیز موفق بوده‌اند. تست GUI وابسته به نمایشگر در runner بدون نمایشگر skip شده است.

نسخه 2.4.1 در تاریخ 17 نوامبر 2026 به‌عنوان نسخه پایدار منتشر شده است. یادداشت انتشار: PyLex Studio 2.4.1.
